# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — start the dev server (Next.js + Turbopack), http://localhost:3000
- `npm run build` — production build
- `npm run start` — run a production build
- `npm run lint` — ESLint (flat config, `eslint-config-next`)

There is no automated test suite (no test runner in `package.json`, no test files). `app/api/uploadPhotos/test.js` and `oldRoute.js` are scratch/alternate implementations left in place, not tests.

## Architecture

This is a Next.js 15 App Router site for a youth sports program (NTX Devils), backed directly by MySQL (via `mysql2`), with photos in S3.

### Data layer: client builds SQL, server executes it verbatim

Every CRUD feature (`app/api/player`, `app/api/sponsor`, `app/api/teams`, `app/api/schedules`, `app/api/info`, `app/api/announcements`, `app/api/admin`) follows the same shape: the client component constructs a full SQL string via JS template literals (including raw user input) and `POST`s it as `{ query }`; the route does nothing but `db.promise().query(request_body)` and returns the raw result. There is no parameterization or query allowlisting anywhere in this path — **the client is trusted to send exactly the SQL that should run.** This is a pre-existing, systemic SQL-injection surface across the whole app, not specific to one route. When adding anything that touches real data (and especially payments/financial records), do not extend this pattern — use parameterized queries in a dedicated server-side route instead.

Canonical schema lives in `database.sql` (idempotent `CREATE TABLE IF NOT EXISTS` statements — this is the source of truth for table shape). `database_calls.sql`, `testing.sql`, and `text_db.sql` are scratch/example query notes, not executed automatically and not kept in sync with the schema.

DB connection config is duplicated per-route (`mysql2.createPool` reading `DBHOST`/`DBUSER`/`DBPASS`/`DBDATABASE` from env) rather than shared from one module.

### Auth is client-side only

"Login" (`app/login/page.js`) compares the entered username/password against `NEXT_PUBLIC_USERNAME` / `NEXT_PUBLIC_PASSWORD` — `NEXT_PUBLIC_*` env vars are inlined into the client bundle, so these credentials are visible to anyone who inspects the page. On success it just sets a boolean in React context (`loginProvider.js`); there is no server-side session, token, or route protection. Admin pages check `login` from context client-side (e.g. `app/loggedin/page.js`) and redirect if false, but nothing stops calling the admin API routes directly.

### Global state via three React Contexts

`app/Providers.js` wraps the app in `TeamProvider` (`teamChoice.js`), `LoginProvider` (`loginProvider.js`), and `PlayerProvider` (`playerChoice.js`). These hold "currently selected team/player" and login state in memory (no persistence) — e.g. `app/teams/page.js` sets the selected player into `PlayerProvider`, then `app/player/page.js` reads it back from context and redirects to `/teams` if nothing is set (there's no `/player/[id]` route — navigation depends on context being populated first).

### Schema shape

Core tables (`database.sql`): `program` → `team` → `roster` (players), `info`, `announcements`, `event` with `schedule` as a team↔event intersection table, `sponsor` (organizational/business sponsors — name, level, website, phone, bio, photo; unrelated to per-player donations), `photo` with `photo_intersection` joining photos to team/roster/event. `roster.sponsor_link` was a plain admin-entered URL rendered as a "Sponsor {player}" link on the player page; it has been superseded by the Stripe sponsorship flow below (the column/admin UI for it still exist but the player page no longer reads it).

`player_sponsors` / `player_sponsorships` (added for the per-player donation feature) are intentionally named apart from `sponsor` to avoid clashing with the existing organizational-sponsor concept.

### Photo uploads

`app/s3.js` and `app/api/uploadPhotos` / `app/api/deletePhotos` upload to a hardcoded S3 bucket (`ntxdevils`, `us-east-2`) via `aws-sdk` v2, keyed by a `folder` field (e.g. `"sponsors"`, roster photos) so different admin flows land in different S3 prefixes.

### SMS admin bot (experimental)

`app/api/text/route.js` implements a Twilio-driven, numeric-state-machine "admin via text message" flow backed by a single-row `new_text` table holding session state (`curr_status`, in-progress field values). It mirrors the same raw-SQL-string pattern as the rest of the app. Treat this as unfinished/experimental (see `app/api/text/psuedocode.txt`, `text_switch_case_logic.txt`) rather than a maintained feature — there are known bugs (e.g. a malformed query in the `case 23` exit branch, an undefined `senderNumber` reference).

### Player sponsorship payments (Stripe + Venmo/Zelle/PayPal/Other self-report)

Flow: `app/player/page.js` renders `app/SponsorForm.js` (client component) when the selected player has an `id` (see roster id note above). The method picker only shows **Venmo/Zelle/PayPal** (the three the club actually has handles for) at the top of the form, followed by payer identifier → name → email → amount. Card (Stripe) and Other are hidden from `METHODS` but their code paths are left intact and dormant — re-adding either is just adding it back to that array, not rebuilding. Whichever method is picked branches into one of two paths:

**Card (Stripe) — automatically confirmed:**

1. `POST /api/create-checkout-session` (`app/api/create-checkout-session/route.js`) creates a Stripe Checkout Session in `ui_mode: 'embedded'`, with `roster_id`/`sponsor_name`/`sponsor_email` in `metadata` and a dynamic `price_data` line item for the entered amount (card only, no pre-created Stripe Product). Returns `clientSecret` to the client.
2. The client mounts `EmbeddedCheckoutProvider`/`EmbeddedCheckout` (`@stripe/react-stripe-js`) with that `clientSecret`; on `onComplete` it just shows a thank-you message — no DB write happens client-side.
3. `POST /api/webhooks/stripe` (`app/api/webhooks/stripe/route.js`) is the only place that writes a **`confirmed`** `player_sponsorships` row for this path. It verifies the Stripe signature, reads `checkout.session.completed`, upserts the sponsor into `player_sponsors` by email, and inserts using **`session.amount_total`** (the actual charged amount from Stripe, not client-supplied metadata) and parameterized queries. It's idempotent on `stripe_checkout_session_id` since Stripe may redeliver webhook events. This route has its own inline sponsor-upsert logic (not the shared `createRow` helper below) since it also needs idempotency-by-session-id and to persist the Stripe ids — kept separate deliberately rather than complicating the generic admin resource.

**Venmo / Zelle / PayPal / Other — self-reported, manually reconciled:** Venmo and Zelle have no merchant API (Zelle has no deep-link standard either — purely bank-app-to-bank-app), so neither can be confirmed programmatically. PayPal actually does have a real Checkout/webhook API like Stripe's, but this build intentionally treats it the same as Venmo/Zelle (self-report, not a second automated integration) to keep one reconciliation path — worth revisiting if PayPal volume grows enough to justify the same webhook treatment as Stripe. Picking a method shows: Venmo's real pay-prefill link (`https://venmo.com/<NEXT_PUBLIC_VENMO_USERNAME>?txn=pay&amount=...&note=...`), the club's Zelle contact (`NEXT_PUBLIC_ZELLE_CONTACT`), or a `paypal.me/<NEXT_PUBLIC_PAYPAL_HANDLE>/<amount>` link — plus a field asking the *sponsor's own* Venmo username / phone / PayPal email so there's something to match against incoming payments (stored as `payer_identifier`).

Clicking "Open Venmo/PayPal to Pay" (or "Continue" for Zelle) does three things: fires (not awaited, so it never blocks the UI transition) `POST /api/sponsorships/started`, which **creates the `player_sponsorships` row right then** with `sponsorship_status: 'user_started'` (not just an email — this is deliberate, so an admin can see "started but never confirmed" attempts, not only ones that made it all the way through) and sends the "process started" email; the returned row `id` is captured async into `sponsorshipId` state once the response resolves. It also opens the payment app in a new tab and flips the current tab to a **"Sponsorship Pending"** screen with the same fields shown again, editable (in case the sponsor ends up paying from a different Venmo/PayPal identifier than they typed). Clicking **"I've Sent the Payment"** there `POST`s to `/api/sponsorships` (`app/api/sponsorships/route.js`) with that `sponsorshipId` — if present, it **updates the same row** (via `updateRow`, not a new insert) setting `sponsorship_status: 'user_confirmed'`; if absent (e.g. the `/started` call failed or got skipped), it falls back to creating a fresh row so the endpoint still works standalone. `status` (a separate, older column — see below) is still always forced to `'pending'` here; the client can never set either field to a club-confirmed value directly. Both routes send their respective notification email non-blockingly (a failed send never fails the request). An admin then reconciles rows against actual bank/Venmo/Zelle/PayPal activity (matching on `payer_identifier`) from the **Sponsorships** tab in `/adminPortal`.

**Mobile app opening (Venmo/PayPal):** `SponsorForm.js` detects mobile via a SSR-safe `navigator.userAgent` check (only ever affects which URL a click handler uses, never rendered JSX, so there's no hydration risk). Verified via research, not assumed: PayPal.me links already hand off to the installed app on mobile through standard OS-level universal/app links — no code needed, the existing `paypal.me/...` URL just works. Venmo doesn't do this on its own, so on mobile the button instead tries Venmo's custom URI scheme (`venmo://paycharge?txn=pay&recipients=...&amount=...&note=...` — confirmed still current, but it's undocumented/reverse-engineered and Venmo has broken it before, so it's not guaranteed reliable long-term) via `window.location.href`, with a simple fallback: if the tab is still visible ~1.5s later (app never took over, e.g. not installed), it opens the existing web link instead. No app-store-redirect/deferred-deep-linking complexity was added — deliberately out of scope.

**`sponsorship_status` is the one lifecycle field the admin UI actually reads** (`player_sponsorships.sponsorship_status`, plain `VARCHAR`, no DB-level enum): `null` (nothing happened / unknown), `'user_started'`, `'user_confirmed'`, `'club_confirmed'`, `'club_rejected'`. This replaced an earlier design with three separate flag columns (`sponsorship_started`/`sponsor_confirmed`/`club_confirmed`) — that fell apart because any update touching one flag risked clobbering the others back to null (needed `COALESCE` gymnastics to avoid it); a single field sidesteps the whole problem since there's only one value to overwrite as the lifecycle advances. The much older `status` column (`'pending'`/`'confirmed'`) is unrelated and still exists solely because the Stripe webhook path and generic `required` validation reference it — it is **not** shown anywhere in the Sponsorships admin table anymore and the two columns are never reconciled with each other; don't assume they agree.

**Admin Sponsorships tab (`/adminPortal`):** `app/AdminCrudTable.js` renders every admin resource as rounded, gapped entry-cards (not a plain `<table>`) via flex rows, so per-entry corners/spacing/backgrounds are stylable — this applies to all tabs, not just Sponsorships. A column config with `secondRow: true` (currently `payer_identifier`/`sponsor_name`/`created_at`/`amount` in `SPONSORSHIPS_COLUMNS`, paired to a specific row-1 column via `alignWith` so it renders directly under that column rather than just sharing the row's flex distribution) makes that field render on a second, visually-grouped row per entry with its own header line, light gray on both (`bg-gray-200`/`bg-gray-100`) — all cell text is centered, and Actions is always on row 1 (a fixed `w-36` column, with row 2 reserving a matching blank spacer so both rows' flex columns stay equal width — this alignment broke once already from a missing spacer, watch for that class of bug if this markup changes again). A column can also set `narrow: true` (used for `id`) to render as a fixed `w-16` instead of sharing equal width with the rest. `renderCell` supports a per-column `render(val, row)` override: the `sponsorship_status` column uses this to map the five states above to a label/color (`SPONSORSHIP_STATUS_DISPLAY` in `configs.js`; unrecognized/null renders as a plain dash rather than guessing), `amount` formats as `$X.XX`, `created_at` converts the UTC timestamp to `America/Chicago` via `toLocaleString` (must use explicit `year`/`month`/`day`/`hour`/`minute` options, not `dateStyle`/`timeStyle` — combining those with `timeZoneName` throws `RangeError: Invalid option : option`, a real spec restriction that broke this page once). The Sponsorships tab config sets `confirmField: 'sponsorship_status'`, `confirmValue: 'club_confirmed'`, `rejectValue: 'club_rejected'`, which swaps the row actions from generic Edit/Delete to **Confirmed** (`PUT`s the full row with `sponsorship_status: confirmValue`) and **Not Received** (same `PUT` with `rejectValue`) — both fully generic in `AdminCrudTable.js` off those three config keys, no hardcoded field/value names in the component. When a row's `sponsorship_status === rejectValue`, the entire row (both lines) renders in red (`text-roseRed`) as a clear visual flag. This is the one resource that doesn't get the standard edit modal for its row actions — correcting other fields (amount, sponsor info) on a sponsorship currently has no admin-UI path since Edit was removed for this resource; only direct DB access or a future edit-affordance would do it.

**Sponsorships Excel export:** the Sponsorships tab has an "Export to Excel" link/button (`config.exportUrl`, a generic key `AdminCrudTable.js` checks on any tab config — only set for Sponsorships today) pointing at `GET /api/adminData/sponsorships/export` (`app/api/adminData/sponsorships/export/route.js`, using the `xlsx`/SheetJS package). It reuses the same `listRows('sponsorships', ...)` call the table itself uses (no separate query), then splits rows into three sheets by `sponsorship_status`: **Confirmed** (`club_confirmed`), **Not Received** (`club_rejected`), and **Pending** (everything else — `null`/`user_started`/`user_confirmed`). The Pending sheet carries an extra `Status` column with the raw value, since "pending" otherwise conflates three meaningfully different states (sponsor hasn't started, started but not confirmed, confirmed but not yet reviewed by the club) that an admin doing reconciliation needs to distinguish. `created_at` is formatted the same America/Chicago way as the admin table (explicit `year`/`month`/`day`/`hour`/`minute` options — combining `timeZoneName` with `dateStyle`/`timeStyle` throws, per the `RangeError` already hit once on this page).

### Player dues (admin-managed, not self-reported)

`dues` is a one-row-per-player table (`roster_id INT UNIQUE`, enforced at the DB level — a second `create` for the same player fails with a raw MySQL "Duplicate entry" error, not a friendly message) holding `dues_paid`/`dues_partial` booleans and `dues_amount_paid`. Unlike Sponsorships, there's no self-report flow at all — an admin sets these directly via the **Dues** tab in `/adminPortal`, which (unlike Sponsorships) keeps the **standard Edit modal** rather than a `confirmField` quick-toggle, because dues needs a free-text dollar amount alongside the two flags, which the `confirmField`/`confirmValue`/`rejectValue` mechanism can't express (it only picks between two fixed values). This did require adding `type: 'checkbox'` support to `AdminCrudTable.js`'s edit modal (a plain checked/onChange input, following the same branch-per-type pattern as `'select'`/`'multiselect'`/`'image'`) — it didn't exist before this feature.

The `resources.js` entry is fully declarative (`selectSql`/`insertColumns`/`updateColumns`, no custom `list`/`create`/`update` needed) — simpler than `sponsorships`/`schedules`/`photos` since there's no intersection table or multi-row side effect, just a straight join to `roster`/`team` for display. `DUES_COLUMNS` in `configs.js` reuses the same field (`dues_paid`) twice with different roles — a display-only `tableCol: true, editable: false` entry with a `render(val, row)` computing **Paid** (green) / **Partial** (yellow) / **Unpaid** (gray — always shown, never a dash; unlike Sponsorships, "nothing set" here has an unambiguous meaning) from `dues_paid`/`dues_partial` together, and a separate plain `type: 'checkbox'` entry (same `key`, no `tableCol`) that only shows up in the edit form. `AdminCrudTable` filters columns into disjoint sets by their flags (`tableCol`/`editable`/`secondRow`), not by deduping on `key`, so this works without any special-casing — don't assume `key` has to be unique across a resource's column array.

The Dues tab also sets `tightRows: true` (flush entry cards, no gap between them, corners still rounded per-card) and `zebraRows: true` (alternates each card's background between `bg-white`/`bg-gray-50` by row index) on its tab config in `configs.js` — both are generic opt-in flags on `AdminCrudTable.js`, not Dues-specific code, and are not set on any other tab (Sponsorships uses `tightRows` alone, since its two-row-per-entry layout already has its own gray second-row banding).

**Data entry note:** the initial ~23 rows were loaded from a hand-written list of nicknames/first-names (e.g. "D Mase" → Daniel Mason, "Pooj" → Sean Poojaroen, "Orry" → David Orr) cross-checked one-by-one against the live roster — a few were skipped rather than guessed: "John M" (ambiguous between two actual players, John Mannion and John Morey), "Kirk" and "Flash" (no matching roster entry at all, and no plausible nickname candidate either). "Dylan" resolved to "Dylan Lord," who did not yet exist in `roster` (he'd shown up in an earlier PlayHQ sub-squad import that was mistakenly assumed already covered) — added to the roster (Men) before attaching his dues record, rather than silently dropping a real payment. If any of these turn up later, they'll need manual entry via "+ Add Dues" — the `roster_id` field there is a normal `select` (`optionsKey: 'players'`) covering the whole roster, not just these 23.

**Email notifications to the club (`app/api/mailer.js`):** a thin Gmail SMTP wrapper via `nodemailer` (`service: 'gmail'`, `GMAIL_USER`/`GMAIL_PASSWORD` from env — these existed unused in `.env.local` before this; there was no prior contact-form/mailer anywhere in the app to reuse). Two emails go to a hardcoded `info@ntxdevils.com` (not an env var — it's the literal address requested, distinct from `NEXT_PUBLIC_ZELLE_CONTACT` even though currently the same value): "Sponsorship process started for X" from `/api/sponsorships/started` when the sponsor clicks the pay/continue button, and "Sponsor confirmed payment for X" from `/api/sponsorships` when they click "I've Sent the Payment" — both include sponsor name/email, payment method, payer identifier, and amount. Both send calls are wrapped so a mail failure (e.g. bad Gmail app-password) never blocks the sponsor's flow or the DB write.

Required env vars (placeholders added to `.env.local`, values not yet set): `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY`. Webhook needs to be registered in the Stripe dashboard (or `stripe listen` locally) pointing at `/api/webhooks/stripe` for `checkout.session.completed`.

**Getting test-mode keys:** every Stripe account has a Test mode / Live mode toggle in the top-right of the dashboard — flip it to Test mode first (test and live keys/data are completely separate, no extra signup). Then:
- **Developers → API keys** — test **Publishable key** (`pk_test_...`) → `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY`; test **Secret key** (`sk_test_...`) → `STRIPE_SECRET_KEY`.
- **Webhook signing secret** — for local dev, use the Stripe CLI: `stripe listen --forward-to localhost:3000/api/webhooks/stripe`, which prints a `whsec_...` value for `STRIPE_WEBHOOK_SECRET` and forwards real test events without needing a public URL. (Alternatively, Developers → Webhooks → add an endpoint pointed at a publicly reachable URL, e.g. a Vercel preview deploy, for a persistent `whsec_...`.)
- **Test payments** — use Stripe's canned card `4242 4242 4242 4242`, any future expiry, any CVC, any ZIP, for a guaranteed successful charge. No real money moves in test mode.

`NEXT_PUBLIC_VENMO_USERNAME` (`ntxdevils`), `NEXT_PUBLIC_PAYPAL_HANDLE` (`ntxdevils`), and `NEXT_PUBLIC_ZELLE_CONTACT` (placeholder, still unset — the club's official flyer only shows a QR code, no plain-text contact) are public by design — they're just displayed to sponsors, not secrets.

### Admin CRUD convention

Each admin area (`adminTeams`, `adminSponsors`, `adminSchedules`, `adminAnnouncements`, `adminInfo`, `adminPhotos`) follows the same file layout: `page.js` (list/menu), `new.js`, `edit.js`, `delete.js`, each independently building its own SQL string and hitting the matching generic API route.
